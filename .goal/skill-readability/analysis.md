# 스킬 가독성·최소성·중복 분석

- 단계: Analysis. 작성일: 2026-10-25.
- 요청: 현재 디렉터리의 스킬들이 한눈에 읽히는지, minimal한지, 중복된 말이 없는지 분석한다.
- 사용자와 합의한 폴더: `.goal/skill-readability/`.
- 결론: 역할 구분은 대체로 명확하다. `workflow-plan`과 `codebase-design`은 반복 설명을 줄일 여지가 크고, `workflow-define`과 `tdd`는 긴 문장을 나누는 편이 먼저다. 전체를 일괄 축약할 근거는 약하다.

## Concept

- **한눈에 읽힘:** 언제 쓰고, 무엇을 읽어 무엇을 하며, 무엇을 남기고 언제 끝나는지 쉽게 찾을 수 있는가.
- **Minimal:** 실행 판단에 필요한 내용은 남고, 판단을 바꾸지 않는 설명은 적은가. 줄 수 자체가 기준은 아니다.
- **중복:** 같은 규칙을 여러 곳에서 각각 유지해야 하는가. 같은 용어의 등장보다, 규칙을 고칠 위치가 여러 개인지가 중요하다.

반복이 모두 낭비는 아니다. description은 선택할 때, 본문은 실행할 때 읽는다. 두 곳의 짧은 역할 요약, 템플릿의 필드명, 오류를 구분해 주는 예시, 단계 사이의 연결 설명은 유지할 이유가 있다.

## Context

직접 읽은 범위는 `.agents/skills/`의 `SKILL.md` 10개와 부속 문서 4개, 루트 `AGENTS.md`다. `docs/`의 외부 참고 스킬은 제외했다. 기존 분석 문서는 배경으로만 읽고, 아래 판단은 현재 파일에서 확인했다. 이하 스킬 경로는 `.agents/skills/` 기준이다.

글자 수는 frontmatter를 제외하고 공백·Markdown을 포함한 문자 수다. 줄 수는 frontmatter·빈 줄을 포함한다. 분량은 보조 증거이며 품질 점수가 아니다.

- Markdown 상대 파일 링크 10개는 모두 실제 파일로 연결된다. 링크 대상 누락은 발견하지 않았다.

## Problem

### 1. Plan: 같은 계약을 여러 번 설명한다

근거: `workflow-plan/SKILL.md`.

- 9줄의 ticket·수직 조각 설명이 25~32줄에서 다시 나온다. 29~31줄의 구체적 조건은 유용하지만 25줄은 새 정보를 더하지 않는다.
- 36~44줄에서 Blocked by·Owner·Parallel·Checks·Covers를 정의하고, 48~53줄에서 발표 항목 일부를 다시 열거한 뒤, 75~91줄에서 템플릿으로 다시 보여 준다.
- 67줄은 파일 하나당 ticket 하나라는 말을 두 차례 강조한다. 앞의 65줄도 승인된 ticket을 쓰라는 안내다.
- 69줄의 frontier 작업 지시는 Plan의 산출물 작성 절에 있다. 순서를 설계하라는 뜻인지, 실제 ticket을 시작하라는 뜻인지 흐리다. 실행 규칙은 Execute에도 있다.

**영향:** ticket 조건을 확인하려면 절차와 템플릿을 오가고, 필드 변경 시 여러 목록이 어긋날 수 있다.

**방향:** 필드 정의 위치를 하나로 정하고, 절차에는 작성 순서·승인·예외를 남길 수 있다. 복사할 템플릿과 분할 승인 절차는 고유한 효용이 있다.

### 2. Codebase Design: 용어 참조와 설계 학습이 섞인다

근거: `codebase-design/SKILL.md`.

- 8줄, Depth 정의인 20줄, 그림 설명인 32~52줄이 작은 interface 뒤에 많은 behavior를 둔다는 중심 개념을 설명한다.
- 99~103줄의 Relationships는 앞서 정의한 용어의 관계를 다시 열거한다. 연결을 돕지만 재진술 비중이 높다.
- Interface를 좁게 해석하지 말라는 내용은 16·108줄에, boundary를 피하라는 내용은 12·22·109줄에 분산돼 있다.
- 71~93줄의 설계 예시는 기본 본문에 있다. Define과 TDD는 이 스킬을 공통 용어 참조로 호출한다(`workflow-define:18`, `tdd:24`).

**영향:** 용어 하나를 확인하려는 호출자도 설계 예시와 반복 설명까지 읽게 된다.

**방향:** 기본 본문은 용어와 판단을 바꾸는 원칙에 집중하고, 그림·설계 예시·상세 관계는 심화 문서로 옮길 수 있다. Glossary 자체를 없앨 근거는 없다.

### 3. Define과 TDD: 짧은 파일에 여러 지시를 압축했다

- `workflow-define:18`은 Evaluation의 구성, 평가 불필요 예외, 코드 목표 조건, 다른 스킬 로드, seam 기재를 한 bullet에 넣었다. 산출물 정의와 조건부 행동이 섞인다.
- `workflow-define:20~22`는 tree의 깊이, 질문 범위, 평가 질문의 발생, Round별 기록을 연속 문단에 담았다.
- `tdd:22`는 사전 합의, Evaluation→Checks 연결, 미확정 seam 금지, 테스트 노력 배분의 이유를 한 문단에 담았다.
- `tdd:24,29,30`도 호출 조건·용어 목록이나 정의·이유·실행 방식을 긴 문장으로 묶는다. 36줄인 TDD의 본문 글자 수는 98줄인 Plan의 약 85%다.

**영향:** 짧아 보여도 조건을 다시 찾기 어렵다. 더 축약하면 필요한 조건까지 빠질 수 있다.

**방향:** 산출물 정의와 조건부 행동을 나누고 한 항목에 한 지시를 두는 편이 낫다. 실행 판단을 바꾸지 않는 이유는 압축 후보지만 Evaluation과 seam 연결은 유지할 기능이다.

### 4. Execute: 역할 소개와 절차가 겹치고 종료 의미가 갈린다

- `workflow-execute:11~21`의 task graph·subagent·orchestrator·Owner별 처리 설명이 25~38줄의 Steps와 일부 겹친다.
- 17줄은 상태 기록·커밋을 역할로 설명하고, 34줄은 구체적인 행동으로 다시 지시한다.
- 9줄은 모든 ticket이 done인 전체 구현을 목표로 하지만, 42줄은 done·incomplete·blocked 중 하나와 Check 결과가 있으면 끝이라고 한다.

**영향:** 소개를 기억한 채 Steps를 읽어야 한다. 실행을 마치는 상태와 목표를 달성한 상태도 같은 표현으로 읽힐 수 있다.

**방향:** 행동 규칙은 절차에 모으고 소개는 짧게 할 수 있다. 성공과 중단의 의미를 구분할 필요가 있으며, 그 정책은 후속 결정이다.

### 5. 테스트 원칙은 여러 파일에서 유지된다

- 공개 interface로 behavior를 검증하라는 내용이 `tdd:14,20,28`, `tdd/tests.md:5,19~22,38~45`, `codebase-design:64`, `codebase-design/DEEPENING.md:34~37`에 있다.
- 의존성을 외부에서 받으라는 설명과 예시는 `codebase-design:71~81`과 `tdd/mocking.md:20~35`에 있다.
- internal seam을 자체 테스트에 쓸 수 있다는 `codebase-design:62`와 internals를 테스트하지 말라는 `tdd:20`은 적용할 module 범위를 생략해 함께 읽을 때 해석이 필요하다. 같은 대상을 두고 직접 모순된다고 단정할 수는 없다.

**영향:** 같은 원칙의 변경 위치가 여러 개이고, 적용 범위의 미세한 차이는 독자가 해석한다.

**방향:** 용어는 Codebase Design, 테스트 행동 규칙은 TDD, 예시는 부속 문서가 맡는 구분을 선명하게 할 수 있다. 각 맥락에서 원칙을 짧게 상기시키는 것까지 없앨 필요는 없다.

### 6. 나머지는 작은 압축 후보와 형식 문제다

- **Analysis:** 도입이 description을 다시 풀지만 본문은 334자다. 큰 축약 효과가 없다.
- **Verify:** 8~12·17~19·23줄에서 증거·판정·근거 기록이 재진술된다. UNKNOWN과 독립 판정의 입력 제한은 고유한 규칙이다.
- **Review:** 16·18~20·28줄의 일반 원칙은 압축 여지가 있다. 세 평가 관점과 Accept/Revise/Explore는 역할을 잘 드러낸다.
- **Grill:** 8·26줄은 frontier와 다음 Round의 관계를 반복하지만, 후자는 이번 Round 안에서 서로 의존하는 질문을 함께 묻는 오류를 막는다. 통째로 지울 중복은 아니다.
- **Handoff:** 10·32줄의 강조 문구보다 실행 지시가 이미 구체적이다. 35줄의 이전 재현·검사 반복 금지와 37줄의 상속한 주장 검증은 범위를 구분해야 쉽게 읽힌다. 과거 자료 예시의 `plan.md`는 현재 `tickets/` 규칙과 직접 충돌한다고 볼 수는 없다.
- **공통 형식:** 한국어·영어가 섞이고, Execute·Grill·Handoff에는 다른 스킬과 같은 본문 제목이 없다. 개별 이해보다 스킬끼리 비교할 때 부담이다. 언어·제목 통일 여부는 선호의 문제다.

## 유지할 이유가 있는 구분

- **Evaluation → Checks → 판정:** 목표 기준, 작업별 확인 방법, 실제 증거에 따른 판단은 역할이 다르다.
- **Define → Grill:** 목표의 구성 항목과 인터뷰 진행법을 분리한 구조다.
- **Review와 Verify:** 판단의 적절성 검토와 합의한 기준의 충족 증명은 다르다.
- **description과 본문 요약:** 선택 시점과 실행 시점이 다르다.
- **본문과 예시:** 실패 유형을 식별하게 돕는 예시는 같은 주제여도 추가 정보다.

## 남은 불확실성

확인할 사실:

- 실제 에이전트가 어떤 반복을 활용하고 긴 문장에서 어떤 규칙을 놓치는지는 측정하지 않았다. 이번 판단은 정적 읽기에 근거하며 행동 개선을 입증한 결과는 아니다.
- 부속 문서의 실제 참조 빈도와 공통 용어 호출의 읽기 부담은 측정하지 않았다.
- internal seam, Execute 중단, Handoff 재검증 범위가 실제 혼선을 일으켰는지는 별도 사례가 필요하다.

사용자가 정할 것:

- 우선 독자가 사람인지, 실행하는 에이전트인지, 둘 다인지.
- 한국어·영어 혼용을 유지할지, 언어·제목 형식을 맞출지.
- 각 스킬을 단독으로 읽을 수 있어야 하는지, 공통 문서 참조를 얼마나 허용할지. 참조를 늘리면 본문은 짧아지고 이동 비용은 커진다.
- 복사 편의를 위해 템플릿을 본문에 둘지, 별도 문서로 뺄지.

이번 단계에서는 분석 문서만 작성했다. 수정 범위·요구사항·평가 기준은 정하지 않았으며, 스킬 원문은 변경하지 않았다.
