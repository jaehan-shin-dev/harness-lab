goal과 plan의 경계

"plan은 작업 카드 한 장만 읽어도 구현할 수 있게 쓰고, 구현은 subagent에게 맡기면 좋겠다. Matt은 goal과 plan을 합친 spec으로 구현하는 것 같다." 이 생각이 맞는지, 다른 스킬들은 어떻게 하는지, 지금 방식을 그대로 둬도 되는지 살펴봤어요. 요약과 결정할 질문은 같은 폴더의 analysis.md에 있어요.

원문 스킬 파일의 문장 해석 내 추론 사실 내 기록에서 확인한 것

한 줄 답

문서 두 장(goal, plan)은 그대로 두고, plan의 작업 카드와 Plan 단계의 인터뷰 방식을 바꾸는 쪽이 유리해 보여요.

  • Matt에 대한 추정은 반만 맞아요. Matt은 목표와 설계 결정을 spec 한 장에 합쳐요. 그런데 그다음에 작업 카드(ticket)로 다시 나눠요. 그래서 Matt도 문서가 두 장(spec과 tickets)이에요.
  • "파일까지 적힌 카드, 혼자 읽고 구현"은 superpowers 방식이에요. Matt은 오히려 카드에 파일 경로를 쓰지 말라고 해요. 두 방식은 파일 경로에 대해 정반대예요.
  • 진짜 차이는 장 수가 아니에요. ① 작업 카드에 "다 됐는지 보는 기준"이 들어 있나, ② 인터뷰를 몇 번 하나, 이 두 가지예요.
  • subagent 구현은 일이 여러 파일로 쪼개질 때만 이득이에요. 최근 목표는 파일 1~2개였어요. pi는 이 저장소에서 subagent를 쓸 수 없어서, 카드 하나마다 새 세션으로 시작하는 Matt 방식이 세 하네스 모두에서 돌아가요. 해석

레고로 비유하면

goal.md는 완성 사진과 검사표예요. 무엇을 만들지, 다 만들면 무엇을 확인할지 적혀 있어요. plan.md는 조립 설명서예요. 같은 레고를 네 가지 방식으로 맡긴다고 생각해 볼게요.

지금 나사진 뒷면에 다 적고, 설명서는 "뒷면 참고"

완성 사진(goal.md) 뒷면에 부품 위치까지 꼼꼼히 적어요. 설명서(plan.md)에는 "1. 바퀴 만들기, 사진 뒷면 3번 참고"라고만 써요. 사진을 만들 때도, 설명서를 만들 때도 나한테 하나하나 물어봐요.

카드만 봐서는 "바퀴가 다 됐는지" 알 수 없어요. 확인 기준은 사진 쪽 검사표에 있어요.

Matt설계 메모 한 장 + 봉투마다 미션 카드

완성 사진과 설계 메모를 한 장(spec)으로 만들고, 봉투마다 미션 카드(ticket)를 붙여요. 카드에는 "이 봉투로 바퀴가 굴러가게 만들기 / 확인: 바퀴 네 개가 돈다 / 봉투 1이 끝난 뒤에"만 적어요. 부품 번호는 적지 않아요. 금방 바뀌기 때문이에요.

친구는 카드와 설계 메모를 보고 상자를 직접 뒤져서 부품을 찾아요. 카드 하나마다 새 친구(새 컨텍스트)가 와요.

superpowers페이지마다 부품 번호까지

설명서 페이지마다 "3021번 부품 두 개를 여기에"까지 적혀 있어요. 친구는 자기 페이지만 보고 만들어요. 옆 페이지 친구가 어떤 부품 이름을 쓰는지는 "주고받는 부품" 칸(Interfaces)을 보고 알아요.

대신 친구들은 동시에 만들지 않고 한 명씩 차례로 만들어요.

파일이 부딪칠 때두 친구가 같은 부품을 동시에 끼우면

서로 부딪쳐요. 자료들은 세 가지로 피해요.

내 방식의 장점과 단점

장점

  • 합격 기준이 실행 전에 따로 고정돼요. goal.md Evaluation(Criteria, Method, Evidence)이 있어요. Matt spec에도 Testing Decisions(좋은 테스트의 기준, 시험할 모듈, 선례)는 있어요 to-spec:59-65. 하지만 요구사항마다 확인 방법과 증거를 적는 표는 없고, 카드의 합격 기준과 끝의 Spec 축 리뷰가 그 일을 나눠 맡아요. 이 기준은 독립 Verify에 그대로 넘길 수 있어요. addy는 검증자에게 "결론은 말고 산출물과 기준만" 주라고 해요 doubt-driven:106.
  • 결정이 기록으로 남아요. [합의 Qn] 표시가 있어요. Matt은 용어집과 ADR로, superpowers는 "your call" 표시로 같은 일을 해요.
  • 사람이 할 일을 구분해요. Responsibility(AI / User) 칸이 있어요. 평가 세션 실행처럼 사람 손이 필요한 일이 많은 내 작업에 맞아요.
  • subagent 없이도 돌아요. pi를 포함한 세 하네스 모두에서 같은 흐름이 돌아요.

단점

  • 작업 카드가 혼자 서지 못해요. 카드에 "다 됐는지 보는 기준"이 없어요. Checks는 "어떻게 점검하나"라는 과정 기준이에요 plan:13.
  • 인터뷰를 두 번 해요. Define에서 한 번, Plan에서 또 한 번이고 둘 다 모든 결정을 물어요. Matt은 한 번 묻고, 그다음은 정리와 쪼개기 확인만 해요.
  • 경계를 "높이"로 그어서 양쪽 증상이 다 나왔어요. Define이 무거워졌고(Round 6, Q27, goal.md 125줄), 그런데도 Plan에서 goal.md로 되돌아갔어요(Plan Q13) 사실.
  • 카드 크기와 파일 겹침 규칙이 없어요. 나중에 subagent에게 맡길 때 기준이 없어요.

goal.md(무엇, 왜, 평가)는 그대로 둬요. plan의 작업을 카드로 바꿔요. 칸은 무엇이 되나, 합격 기준(goal.md R·C와 연결), 막는 카드, 담당이에요. Plan은 인터뷰하지 않고 goal.md에서 정리한 뒤 쪼갠 모양만 확인받아요.
얻는 것
혼자 서는 카드, 인터뷰 한 번이에요. 카드마다 새 세션으로 해도 되고 같은 세션에서 차례로 해도 돼서 하네스와 상관없어요.
비용
plan 스킬을 다시 써야 해요. "어떻게"를 goal과 plan 중 어디에 둘지 먼저 정해야 해요.

CB에 superpowers식 세부 + subagent

방법
B의 카드에 파일, 인터페이스, 단계까지 적고 구현은 subagent에게 맡겨요.
얻는 것
바로 넘길 수 있고, 파일 겹침이 미리 보여요.
비용
plan이 길어져요. superpowers도 "plan이 코드보다 길면 코드를 쓴 것"이라고 경고해요 writing-plans:157. pi에는 subagent가 없고, 작은 목표에는 과해요.

B와 C를 가르는 기준은 일의 크기예요.

  • pstack은 "파일 1~2개에 접근이 뻔하면 plan을 건너뛴다"고 해요 multi-phase-plan:5.
  • superpowers는 일의 크기에 따라 거칠 단계를 정해요 brainstorming:134-140.
  • 최근 목표는 SKILL.md 한 개(workflow-handoff), 스킬 7개를 고르게 고치는 일(workflow-skill-fix)이었어요 사실. 독립 파일 여러 개로 나뉘는 일이 얼마나 자주 오는지가 C의 가치를 정해요.
  • 그래서 "B를 기본으로 하고, 크면 C를 얹는다"는 모양이 가능해요. 이건 아직 확인하지 않은 가설이에요(analysis.md F2).

지금 개선 후보 세 개와 이어지는 곳

후보goal/plan 경계와의 관계
단계별 산출물plan을 카드로 쓰면 "Execute가 읽는 단위"가 카드 한 장으로 분명해져요. Analysis → Define 연결(analysis.md를 Define이 읽게 하기)은 이것과 별개로 따로 정해야 해요.
단계별 commit자료들이 공통으로 하는 건 단계 끝보다 작업(카드) 끝 커밋이에요. Matt implement:17, superpowers 작업 Step 5, gstack qa:676. 카드가 생기면 커밋 단위도 자연스럽게 생겨요. 단계 끝 커밋은 playbook만 해요.
verify는 독립적으로카드의 합격 기준과 goal.md Evaluation이 독립 검증자에게 넘길 "기준"이 돼요. superpowers는 작업마다 리뷰어가 spec 준수와 품질을 따로 보고, Matt은 끝에 Spec 축 리뷰를 한 번 돌려요.
