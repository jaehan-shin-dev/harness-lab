# workflow-analysis 개선

- 단계: Define. 작성·완료일: 2026-10-29. Q1~Q3 수용 후 재개한 문구 검토도 Q4 수용으로 마쳤다.
- 작업 폴더: `.goal/workflow-analysis/`. 앞선 Analysis에서 사용자와 합의한 폴더를 재사용한다.
- 입력: [analysis.md](analysis.md), [analysis.html](analysis.html), 사용자의 최초 목표·배경·조건과 Define Round 1·2 답변.
- 상태: Define 완료. Q1~Q3의 방향·마무리·검증 방법과 Q4의 [구체적인 변경 문구](change-proposal.md)를 모두 확정했다. 남은 사용자 결정은 없다. 스킬 수정·대화 실행·실제 판정은 아직 수행하지 않았다.
- 표기: [기존 조건]은 사용자의 최초 요청, [합의 Qn]은 이번 인터뷰의 수용 사항, [구체화]는 그 조건을 실행 가능한 내용으로 풀어 쓴 것이다.

## Objective

- [기존 조건] 사용자가 AI와 대화하며 개념·맥락·핵심 문제에 대한 이해를 발전시킬 수 있도록 workflow-analysis를 개선한다.
- [기존 조건] 사용자가 이미 제공한 생각과 정보에서 출발하고, 반응에 따라 설명과 분석을 수정한다.
- [구체화] 스킬이 설명할 대상을 제시하는 데 더해, 대화 중 무엇을 재검토하고 다음 설명에 어떻게 반영할지 실행 행동으로 드러낸다.

## Deliverable

- D1. [합의 Q1] `.agents/skills/workflow-analysis/SKILL.md`의 개선본.
  - 본문에는 스킬만 읽고 실행할 수 있는 간결한 행동 원칙을 둔다.
  - [합의 Q4] 정확한 변경 전·후와 교체할 파일 전체 문구는 [change-proposal.md](change-proposal.md)에 확정했다. 후속 작업은 이 32줄 문구를 D1의 기준으로 적용한다.
  - 목적과 출발점: 사용자의 이해, 이미 제공된 생각·정보·의문 활용.
  - 탐색 관점: Concept·Context·Problem을 유지하고 필요에 따라 오간다.
  - 대화 중 행동: 설명·질문·조사·예시·다른 관점을 상황에 맞게 고른다. 사용자 반응을 근거로 기존 설명과 문제 해석을 재검토한다.
  - 조사와 근거: 확인 가능한 사실은 AI가 조사한다. 사실·해석·가설·미확인을 구별하고 근거의 의미를 설명한다.
  - 기록과 마무리: 현재 질문과 이해·남은 의문을 정리하면 한 차례 탐색을 마치고, 추가 반응이 오면 이어 간다. 목표·범위 확정은 Define에 남긴다.
  - 스킬 이름과 사용 맥락을 유지하고, description도 Q4에서 확정한 문구를 따른다.
- D2. [합의 Q1] 대화 예시는 기존 `analysis.md`·`analysis.html`에 남겨 참고와 검증에 활용한다.
  - 스킬 본문에 예시를 추가하거나 별도 예시 문서를 새로 만들지 않는다.
  - 실행 시 기존 분석 문서를 읽어야 하는 의존성을 만들지 않는다.
- D3. [합의 Q3] 문구 검토와 세 가지 실제 대화 비교의 증거.
  - 비교 입력·스킬 버전·모델·도구 환경, 원본 응답·조사 기록과 항목별 판정을 `.goal/workflow-analysis/` 아래 남긴다.
  - 최종 충족 여부는 Verify에서 `verify.md`에 기록한다. 원본 증거의 세부 파일 구성은 Plan에서 정할 수 있다.

## Requirements

- R1. [기존 조건] 이미 제공된 생각과 정보를 출발점으로 삼는다.
  - 이미 주어진 배경·목적·조건을 반복해서 수집하도록 요구하지 않는다.
  - [구체화] 정리된 목표가 없어도 사용자가 제시한 생각·의문에서 탐색을 시작할 수 있다.
- R2. [기존 조건] 설명·질문·조사·예시·다른 관점을 상황에 맞게 사용한다.
  - [구체화] 질문은 정보 보충 외에 관점·전제를 이해하고 해석을 구별하는 데에도 사용할 수 있다.
  - 사용자의 이해에 필요한 수단을 선택하며, 모든 수단을 매번 사용하도록 요구하지 않는다.
- R3. [기존 조건] 사용자의 반응에 따라 설명과 분석을 수정한다.
  - [구체화] 질문·반론·새 정보를 받으면 기존 설명과 문제 해석을 재검토하고, 근거에 따라 필요한 부분을 수정한다.
  - 사용자가 무엇을 왜 바꾸었는지 알 수 있게 설명한다. 반론에 근거 없이 동의하거나 같은 설명을 반복하는 것으로 대체하지 않는다.
- R4. [기존 조건] 필요한 사실 조사는 AI가 수행하고, 사용자가 판단할 근거를 설명한다.
  - [구체화] 확인한 사실과 해석·가설을 구분하고, 근거가 설명을 어디까지 뒷받침하는지 알린다.
  - 확인할 수 없는 사실은 불확실성으로 남긴다. AI가 직접 알 수 없는 사용자 경험·맥락은 질문할 수 있다.
- R5. [구체화] Concept·Context·Problem을 탐색 관점으로 유지한다.
  - 순서대로 모두 설명하는 고정 절차로 강제하지 않는다.
  - 핵심 문제의 해석도 새 근거에 따라 달라질 수 있다.
- R6. [합의 Q2] 현재 요청한 탐색을 다루고, 현재 이해와 남은 의문·이견·불확실성을 정리하면 한 차례 탐색을 마친다.
  - 결과는 `.goal/<goal>/analysis.md`에 기록한다.
  - 설명·문서 작성 완료를 사용자의 이해·동의로 간주하지 않는다. 반응에서 드러나지 않은 이해·동의를 확인된 것으로 기록하지 않는다.
  - 매번 “이해했나요?”라는 확인 질문이나 승인을 요구하지 않는다.
  - 추가 질문이나 반론이 오면 분석을 이어 간다.
  - 기록의 의미가 구분되면 충분하며, 모든 문장에 고정된 분류 태그를 붙일 필요는 없다.

## Constraints

- C1. [기존 조건] Analysis의 목적은 사용자의 이해로 유지한다.
- C2. [기존 조건] 질문 횟수나 고정 인터뷰 순서를 강제하지 않는다.
- C3. [기존 조건] 목표와 범위의 확정은 Define에 남겨 둔다.
- C4. [기존 조건] COFA에 한정하지 않고 일반적인 문제 탐색과 AI 협업에 적용한다.
- C5. [합의 Q1] 본문은 간결한 행동 원칙으로 구성한다.
  - 실행 판단과 직접 관련된 내용은 남기되 긴 해설·대화 예시·중복 규칙을 추가하지 않는다.
  - 임의의 글자 수나 줄 수 제한은 두지 않는다.
- C6. [합의 Q3] 새 평가 도구를 만드는 작업을 포함하지 않는다.
  - 문구 검토와 짧은 실제 대화 비교로 확인한다.
  - 기존 도구의 증거를 그대로 제시하거나 가상 대화를 작성하는 것으로 실제 응답 확인을 대신하지 않는다.

## Evaluation

[합의 Q3] 문구 검토와 아래 세 상황의 실제 대화 비교를 함께 수행한다. 세 상황은 검증용 사례이며, 스킬의 질문 횟수나 대화 순서에 대한 규칙이 아니다.

### 실제 대화에서 확인할 세 상황

- S1. 이미 충분한 배경·생각·조건을 제공한 상황.
  - 제공된 내용을 활용해 탐색을 시작하는지 확인한다.
  - 이해를 돕는 설명·예시 등 필요한 행동을 고르는지 확인한다.
  - 한 차례 탐색을 마칠 때 현재 이해와 남은 의문을 기록하며, 사용자 이해·동의를 임의로 확정하거나 Define으로 자동 진행하지 않는지도 확인한다.
- S2. 사용자가 AI의 해석에 반론하거나 새 정보를 제공한 상황.
  - 기존 설명과 문제 해석을 재검토하고, 수정이 필요한 부분과 근거를 다음 응답에 반영하는지 확인한다.
- S3. 사용 가능한 자료·도구에서 사실 확인이 필요한 상황.
  - AI가 직접 사실을 확인하고, 출처·확인한 사실·해석과 확인하지 못한 내용을 구별해 설명하는지 확인한다.

### 비교 방법과 증거

- 각 상황에서 기존·수정 스킬에 같은 초기 입력과 후속 사용자 발화를 사용한다. 비교 가능한 모델·도구 환경과 별도 컨텍스트를 사용한다.
- 사례 입력과 성공 조건은 응답을 보기 전에 정한다. 구체적인 발화와 실행 수단은 Plan에서 정할 수 있다.
- 원본 응답과 실제 조사 기록을 보존하고, 아래 R·C 항목마다 증거를 인용해 PASS·FAIL·UNKNOWN을 기록한다. 도구 접근 등 실행 조건이 충족되지 않은 항목은 UNKNOWN과 이유를 남긴다.
- 문구 검토는 모든 R·C를 대상으로 하며, 실제 대화는 아래 표에서 지정한 항목을 확인한다.
- 성공 판정에는 수정본의 모든 R·C가 충족되어야 한다. 필수 항목에 FAIL·UNKNOWN이 남으면 목표 달성으로 판정하지 않는다.
- 기존·수정 스킬의 관찰된 차이를 함께 기록한다. 차이가 없으면 그대로 기록하며, 세 사례의 결과를 일반적인 학습 효과의 증명으로 확대하지 않는다.
- 스킬 문서를 개선하는 목표이므로 코드 모듈의 seam을 정할 대상은 없다. 평가를 생략하는 R·C 항목은 없다.

## 검증 수단에 대해 확인한 사실

- [사실] 기존 `skill-eval`의 suite는 workflow-define용이다. runner가 `goal.md`를 수집하고 모의 사용자가 질문에 대한 사실을 답하는 구조라, workflow-analysis의 반론·설명 수정 행동을 그대로 평가할 수 없다.
- [근거] [suite.yaml](../../skill-eval/suites/workflow-define/suite.yaml), [runner.py](../../skill-eval/skilleval/runner.py), [mock_user.py](../../skill-eval/skilleval/mock_user.py), [process.py](../../skill-eval/skilleval/graders/process.py).
- [합의 Q3] 새 평가 도구를 만들지 않고, 위 세 상황의 짧은 실제 대화로 비교한다.
- [제한] 도구·문서는 읽기 전용으로 조사했다. 아직 실제 실행이나 모델 인증·네트워크·사용량 확인을 수행하지 않았다.

## 인터뷰 기록과 결정

### Round 1 — Q1~Q3 모두 수용

- Q1. 스킬 본문에는 간결한 행동 원칙만 두고, 대화 예시는 기존 분석 문서에 남길까?
  - 합의: 수용. 예시는 참고·검증에 활용하며 스킬의 필수 의존성으로 만들지 않는다.
- Q2. 현재 질문을 다루고 현재 이해와 남은 의문을 정리하면 한 차례 탐색을 마칠까?
  - 합의: 수용. 매번 이해 확인 질문을 강제하지 않으며, 추가 질문·반론이 오면 이어 간다.
- Q3. 문구 검토에 더해 세 상황에서 기존·수정 스킬의 실제 응답을 비교할까?
  - 합의: 수용. 기존 정보 활용, 반론 이후 수정, 사실 조사와 근거 설명을 확인한다. 새 평가 도구는 만들지 않는다.
- 사용자 답변: “accept all”. Q1~Q3의 권장안에 대한 명시적 수용으로 반영했다.

### Round 2 — Define에서 변경 문구 검토·수용

- 사용자 요청: “변경점을 define단계에서 확인하고 싶어”.
- 대응: [change-proposal.md](change-proposal.md)에 문장별 변경 전·후, 이유와 요구사항 연결, 교체할 파일 전체 초안과 실제 원문 대비 diff를 작성했다.
- Q4. 이 전체 초안을 D1의 산출물 기준으로 확정할까?
  - 권장: 위 문구를 수용하거나, 수정하고 싶은 부분을 반영한 뒤 확정한다.
  - 사용자 답변: “accept”. 전체 문구를 수정 없이 수용했다.
  - 상태: 확정. Q1~Q3 합의도 유지한다.
- Q4 수용으로 Define를 마친다. 이번 단계에서는 목표와 확정 변경안 문서만 커밋하며, 스킬 원문 적용과 실제 대화 비교는 수행하지 않는다.

### 남은 미결정과 실행 시 정할 사항

- 남은 사용자 결정: 없음. Q4의 전체 문구를 확정했다.
- Plan에서 정할 수 있는 사항: 세 사례의 발화·고정 자료, 실제 대화 실행 수단, 원본 증거 파일 구성과 작업 분할. 스킬 문구는 Define에서 검토·확정한다.
- 실제 실행 환경이나 새로운 사용자 결정이 필요한 문제가 발견되면 그 사실을 근거로 재검토한다. 문구의 실제 효과가 확인되었다고 미리 간주하지 않는다.
