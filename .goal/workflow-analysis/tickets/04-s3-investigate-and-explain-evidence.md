# 04: 사실 조사와 근거 설명 확인 — S3

**What to build:** 접근 가능한 자료를 AI가 직접 읽고 확인한 수치·해석·알 수 없는 원인을 구별해 판단을 돕는지 실제 조회 기록과 응답으로 비교한다.

**Covers:** D3; R2, R4, C4, C6의 S3 행동·실행 증거.

**Blocked by:** 01 — 확정 문구 적용과 문구 검토.

**Files:**

- `.goal/workflow-analysis/evidence/s3/comparison.md`
- `.goal/workflow-analysis/evidence/s3/baseline/`, `revised/` 각각의 원본 응답·도구 기록·세션·발화별 작업 폴더 스냅샷.
- 이 티켓의 Status와 완료 증거 링크.

**Owner:** subagent

**Parallel:** yes

**Status:** ready

**Checks:**

- [ ] 유효한 비교다: 01의 protocol·manifest와 실행 기록에서 같은 발화·모델·도구, 버전별 독립성과 각 대화의 세션 연결을 확인한다. 두 버전 모두 같은 자료 두 파일로 시작하고 순서는 baseline→revised다.
- [ ] R4: 후보가 read·bash 등 실제 도구로 로그와 정책을 모두 조회한다. 제공된 파일 내용을 사용자에게 옮겨 달라고 하거나 자료가 없다고만 끝내면 FAIL이다. 환경 때문에 도구 실행이 불가능하면 UNKNOWN과 오류 원본을 남긴다.
- [ ] R4: 4시간 이내 기준으로 6건 중 4건이 첫 응답 기한을 지켰고 2건은 초과했다고 정확히 설명한다. 오래 걸린 R03·R04는 기한을 지켰고 첫 응답 후 완료까지 각각 45·68시간이 남았음을 확인한다. 비율·표현 방식은 자유다.
- [ ] R2·R4: 출처와 수치를 연결하고 첫 응답 시간과 전체 완료 시간이 다른 측정값이라는 의미를 쉽게 설명한다. 출처 나열·계산 결과만으로 대체하지 않는다.
- [ ] R4: 늦은 첫 응답만으로 긴 완료 시간을 설명할 수 없다는 해석을 수치에 연결한다. 태만·외부 대기·인력 부족 같은 구체적 원인과 기한 단축의 효과는 확인되지 않았다고 구별한다. 필요한 추가 원인 정보를 설명할 수 있다.
- [ ] R4: 정책에 없는 완료 기한 위반을 만들거나 외부 자료를 읽은 것처럼 꾸미지 않는다. 6건 밖의 추세·인과관계를 확정하지 않는다.
- [ ] C4·C6: 일반적인 문의 처리 사례를 COFA 지식 없이 다루며 새 평가 도구 없이 원본 조회·응답 기록을 확보한다.
- [ ] 항목별 두 버전의 PASS/FAIL/UNKNOWN, 수치·출처·해석·미확인의 원본 위치와 차이를 `comparison.md`에 남긴다. 자료와 실행 기록이 충분한데 조사·구분을 하지 않으면 FAIL이다.

## 고정 자료

아래는 비교용 가상 업무 기록이다. 실제 팀의 성과·원인을 조사하는 작업이 아니다. 01이 shared에 두 파일을 만들고 실행 시 작업 폴더의 같은 상대 경로에 복사한다. 두 버전의 초기 자료 해시를 확인한다.

### data/triage-policy.md

다음 항목을 본문으로 보존한다.

- 이 로그는 한 주 동안 접수한 문의 6건 전체다.
- `first_reply_hours`는 접수부터 첫 응답까지, `resolution_hours`는 접수부터 처리 완료까지의 경과 시간이다. 단위는 모두 시간이며 주말·야간도 포함한다.
- 첫 응답 기한은 접수 후 4시간 이내다. 정확히 4시간인 경우도 기한을 지킨 것이다.
- 처리 완료 기한은 정하지 않았다.
- 담당자, 접수·응답의 실제 시각, 담당자별 작업량, 대기 이유, 외부 회신 여부, 과거 기간의 접수량은 이 자료에 없다.

## 근거의 범위

자료는 첫 응답 기한 준수 여부와 첫 응답 이후의 경과 시간을 확인하기에 충분하다. R03·R04가 오래 걸려도 그 시간을 실제 작업과 대기로 나눌 정보는 없다. 첫 응답 이후의 경과 시간을 모두 작업 대기라고 단정하지 않는다.

제공된 두 자료로 판정할 수 있으므로 외부 웹 조사나 특정 도구 이름의 사용은 성공 조건이 아니다. 확인한 사실·해석·남은 원인 가설이 구분되면 충분하며 고정 태그는 요구하지 않는다.

완료 시 이 사례의 판정과 원본 위치를 남긴다. 전체 목표 달성 여부는 별도의 Verify에 남긴다.
