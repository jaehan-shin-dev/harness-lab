# 04: 실제 기술 가능성 사례 수행

**What to build:** 승인된 실제 적용 평가의 기술 가능성 사례 한 건을 새 스킬을 명시적으로 지정해 수행한다. 현재 환경에서 확인할 수 있는 작은 기술 질문을 골라 실제 조건에서 실행하고, 명령·출력·필요한 측정·확인 범위와 한계를 함께 남긴다.

**Covers:** O1, D4 (기술 가능성), R1 (실제 기술 가능성), R2, R3, R4, C1 (실제 적용 근거), C2, C3, C4, C5, C6.

**Blocked by:** 01 — 사용자 직접 호출 전용 스킬 등록.

**Files:**

- `.goal/workflow-prototype/prototype/technical-feasibility/` 아래의 최소 실행 코드·입력 자료·실제 출력/측정 증거.
- `.goal/workflow-prototype/prototype/technical-feasibility/result.md` — 질문·실제/대체 조건·실행 안내·관찰·한계·남은 선택.
- `.goal/workflow-prototype/tickets/04-technical-feasibility-case.md` — 실행 시 상태와 Checks 기록만 갱신.

**Owner:** subagent

**Parallel:** yes

**Status:** ready

**Checks:**

- [ ] 실제 적용 요청이 남았다: 새 스킬을 명시적으로 지정한 평가 요청과 선택한 기술 질문을 기록한다. 실제 사용자 아이디어가 없으면 에이전트가 현재 환경에서 실행 가능한 작은 사례를 선택한다.
- [ ] 질문에 필요한 실제 조건을 실행했다: 무엇을 실제로 사용했고 무엇을 대체했는지 밝힌다. 질문의 핵심 조건을 대체한 결과로 실제 API·권한·동작·성능이 확인됐다고 주장하지 않는다.
- [ ] 공개 실행 Interface에서 확인했다: 문서화한 명령·입력으로 최소 실험을 실행하고 실제 출력·오류·필요한 측정값을 보존해 질문의 답과 대조한다. 관찰에 필요한 작은 assertion·측정은 쓰되 제품 수준 테스트 절차를 강제하지 않는다.
- [ ] 재실행 방법과 증거가 있다: 필요한 환경·입력·실행 명령·결과 해석과 제한을 `result.md`에 적고 실제 출력/로그를 보존한다. 실행하지 못한 부분은 이유와 함께 미확인으로 남긴다.
- [ ] 결과가 실행 범위와 맞는다: 질문·관찰·알게 된 것·한계·남은 선택을 보고하고, 부정적 결과도 유효한 발견으로 기록한다. 사용자 선호·채택을 대신 결정하거나 다른 환경·규모까지 일반화하지 않는다. 추가 인간 작업을 티켓 완료 조건으로 만들지 않는다.
- [ ] 변경이 격리됐다: 이 사례 폴더와 자기 티켓만 변경한다. 스킬 본문·정책, 다른 사례·목표·기존 단계 스킬을 수정하지 않고 정식 제품 구현·최종 Verify 판정으로 진행하지 않는다.
- [ ] 부모 단계 커밋 규칙을 따랐다: subagent는 산출물·실행 명령·관찰 근거·남은 한계를 main에 전달한다. 스테이징·커밋은 main이 산출물과 Checks를 확인한 뒤 이 티켓 파일만 순차 처리하고 상태를 갱신한다.

**Execution notes:**

- `../goal.md`가 정한 공개 실행 명령·입력·출력 Seam을 사용한다. 실제 호출 기록과 설정/본문 검토만 한 내용을 구분한다.
- 이 사례는 사용자 승인에 따른 에이전트 수행 평가다. 일반 명시 호출 정책과 사용자 판단 원칙은 유지한다.
- 02·03과 독립이다. 다른 사례나 공유 결과 파일을 수정하지 않고 공유 고정 포트를 사용하지 않는다.
- 실행 증거가 없는 Checks는 이유와 함께 미완료로 보고한다. 핵심 조건 실행 자체가 불가능한 경우 이를 실행 성공으로 기록하지 않는다.
