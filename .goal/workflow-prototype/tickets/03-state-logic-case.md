# 03: 상태·로직 사례 수행

**What to build:** 승인된 실제 적용 평가의 상태·로직 사례 한 건을 새 스킬을 명시적으로 지정해 수행한다. 작은 질문에 관계된 상태와 조작 가능한 시나리오를 제공하고, 에이전트가 실제 공개 조작부를 사용해 상태 변화를 관찰한 결과를 남긴다.

**Covers:** O1, D4 (상태·로직), R1 (상태·규칙·로직), R2, R3, R4, C1 (실제 적용 근거), C2, C3, C4, C5, C6.

**Blocked by:** 01 — 사용자 직접 호출 전용 스킬 등록.

**Files:**

- `.goal/workflow-prototype/prototype/state-logic/` 아래의 조작 가능한 데모·필요한 코드/자산·상태 변화 증거.
- `.goal/workflow-prototype/prototype/state-logic/result.md` — 질문·실행 안내·시나리오·관찰·한계·남은 선택.
- `.goal/workflow-prototype/tickets/03-state-logic-case.md` — 실행 시 상태와 Checks 기록만 갱신.

**Owner:** subagent

**Parallel:** yes

**Status:** ready

**Checks:**

- [ ] 실제 적용 요청이 남았다: 새 스킬을 명시적으로 지정한 평가 요청, 선택한 로직 질문·확인할 규칙·실험 가정을 `result.md`에 기록한다. 사용자 아이디어가 없으면 에이전트가 작은 사례를 선택하며, 실험 가정을 사용자 합의로 쓰지 않는다.
- [ ] 상태와 조작부가 공개됐다: 사용자가 실행해 관련 상태를 보고 조작할 수 있다. 필요한 시나리오와 다시 실행할 방법이 안내돼 있다.
- [ ] 같은 Interface에서 상태 변화를 확인했다: 질문에 필요한 최소 시나리오를 실제 공개 조작부에서 수행하고, 초기 상태·수행한 행동·관찰된 상태와 질문의 규칙을 대조한다. 내부 함수만 호출하는 검사로 데모의 실제 조작 확인을 대신하지 않는다.
- [ ] 증거가 재현 가능하다: 조작 순서, 실제 상태 변화와 필요한 캡처/출력/작은 assertion을 보존한다. 별도 요청 시나리오 세트나 제품 수준 테스트 프레임워크는 만들지 않는다.
- [ ] 관찰과 판단이 구분됐다: 보고에 질문·관찰·알게 된 것·한계·남은 선택이 있고 사용자 확인을 받지 않은 선호·채택은 선택 대기로 남긴다. 부정적 결과나 미확인을 사실대로 기록한다. 추가 인간 작업을 티켓 완료 조건으로 만들지 않는다.
- [ ] 변경이 격리됐다: 이 사례 폴더와 자기 티켓만 변경한다. 스킬 본문·정책, 다른 사례·목표·기존 단계 스킬을 변경하거나 정식 제품 구현·최종 Verify 판정으로 진행하지 않는다.
- [ ] 부모 단계 커밋 규칙을 따랐다: subagent는 산출물·실행 명령·관찰 근거·남은 한계를 main에 전달한다. 스테이징·커밋은 main이 산출물과 Checks를 확인한 뒤 이 티켓 파일만 순차 처리하고 상태를 갱신한다.

**Execution notes:**

- `../goal.md`가 정한 화면·공개 조작부 Seam을 사용한다. 데모 형식은 질문에 맞는 가장 작은 형태로 선택한다.
- 이 사례는 사용자 승인에 따른 에이전트 수행 평가다. 일반 명시 호출 정책과 사용자 판단 원칙은 유지한다.
- 02·04와 독립이다. 다른 사례나 공유 결과 파일을 수정하지 않고 공유 고정 포트를 사용하지 않는다.
- 실행 증거가 없는 Checks는 이유와 함께 미완료로 보고한다. 사용자 선택 대기와 실제 시나리오 실행 여부를 구분한다.
