# Goal: workflow-prototype skill

- 단계: **Define 완료 — 실제 문구 보완 포함**. 목표·요구사항·평가 기준과 실제 SKILL.md 기준 문구에 사용자 합의가 있다.
- 작업 폴더: `.goal/workflow-prototype/`.
- 출발 자료: [analysis.md](analysis.md), [handoff.md](handoff.md).
- 사용자 배경: 기존 스킬을 최대한 참고한 방식으로, 현재 flow에 맞게 적용한다.
- 이 문서는 합의한 목표와 평가 기준이다. 스킬 구현·실제 사례 수행·목표 달성 판정은 후속 단계의 작업이다.

## Objective

- **O1**: 대화만으로 판단하기 어려운 아이디어를 작게 만들어 보고 실행해, 사용자가 근거를 가지고 다음 행동을 결정할 수 있게 한다.
  - 기존 스킬의 질문 우선·작은 제작·직접 관찰 방식을 재사용한다.
  - 사용자의 기존 다섯 단계 흐름과 사용자 요청에 따른 단계 이동 원칙에 맞춘다.

## Deliverable

- **D1**: `.agents/skills/workflow-prototype/SKILL.md`.
  - 확정 문구: [skill-draft.md](skill-draft.md). Q13에서 사용자가 승인한 설명·본문을 기준으로 한다. 실제 스킬 설치는 후속 단계에서 진행한다.
  - 사용자가 직접 호출하는 독립 보조 스킬이다.
  - 질문 파악, 유형별 제작·관찰, 사용자 판단 지점, 결과 보고, 보관·커밋 규칙을 설명한다.
  - 탐색 중 관찰과 최종 목표 검증의 차이를 설명한다.
- **D2**: `.agents/skills/workflow-prototype/agents/openai.yaml`.
  - `policy.allow_implicit_invocation: false`로 사용자 명시 호출 전용 정책을 설정한다.
- **D3**: 필요한 보조 자료와 원문 채택·조정 대응 기록.
  - 보조 자료가 필요하면 새 스킬 디렉터리 안에서 분리한다. 구체적인 분리와 파일명은 합의 범위 안의 구현 판단이다.
  - 출처 대응 기록과 평가 증거는 `.goal/workflow-prototype/` 아래에 남긴다.
- **D4**: 화면·상호작용, 상태/로직, 실제 기술 가능성의 실제 적용 사례 각 한 건과 그 결과 기록.
  - 실제 사용자 아이디어를 우선한다. 없으면 목적에 맞는 작은 사례 선택은 에이전트에 맡긴다.
  - 코드·화면은 해당 질문을 확인할 크기로 만들며 제품 완성도는 요구하지 않는다.

## Requirements

- **R1 — 지원 범위**
  - 화면·상호작용을 보고 판단하는 질문.
  - 상태·규칙·로직을 조작하고 확인하는 질문.
  - 실제 API·권한·동작·성능 등 기술 가능성을 실행해 확인하는 질문.
- **R2 — 독립 사용과 복귀**
  - 기존 다섯 단계 밖의 독립 보조 스킬로 둔다.
  - Analysis·Define 중이나 단독 요청에서 사용자가 직접 호출해 사용할 수 있다.
  - 결과를 보고해 원래 논의로 돌아간다. 새 필수 단계나 자동 단계 이동을 만들지 않는다.
- **R3 — 질문에 맞는 작은 제작과 피드백**
  - 질문 좁히기 → 가장 작은 산출물 제작 → 직접 관찰 → 사용자 피드백으로 진행한다.
  - UI 비교는 우선 3안으로 시작한다. 한 아이디어를 보는 요청이면 1안도 허용한다.
  - 로직은 질문에 관계된 상태와 시나리오를 조작할 수 있게 한다.
  - 기술 실험은 질문이 의존하는 실제 조건을 실행한다. 실제로 확인한 부분과 대체한 부분을 구분한다.
  - 이미 분명한 질문은 다시 묻지 않고 필요한 사용자 결정만 묻는다.
  - 고정 시간·총 반복 횟수나 별도 제품 goal·ticket을 공통 선행 조건으로 요구하지 않는다.
- **R4 — 관찰에 근거한 결과 보고**
  - 화면 선호는 사용자의 판단, 로직은 상태 변화, 기술 가능성은 실제 실행을 근거로 삼는다.
  - 관찰·알게 된 것·한계·남은 선택을 보고한다.
  - 아직 확인하지 못한 사실이나 사용자 선호는 미확인으로 남긴다.
  - 부정적인 실행 결과도 질문에 답한다면 유효한 발견이다.

## Constraints

- **C1 — 원문 재사용과 근거 추적**
  - 기존 스킬을 최대한 참고하되 현재 flow에 맞게 조정한다.
  - 채택한 원문 규칙과 조정 이유를 추적할 수 있게 기록한다.
  - 원문의 규칙과 이번 목표의 조정안을 구분한다. 원문이 제시한 절차를 효과 실증으로 과장하지 않는다.
- **C2 — 기존 단계 원칙 유지**
  - 필요한 단계만 수행하고 단계 이동은 사용자 요청에 따른다.
  - 탐색 결과를 최종 goal.md Evaluation의 목표 달성 판정으로 대신하지 않는다.
  - 기존 Analysis·Define 등 단계 스킬과 AGENTS.md의 규칙은 수정하지 않는다.
- **C3 — 현재 목표의 문서·커밋 규칙**
  - 작업 문서는 `.goal/workflow-prototype/`에 보관한다.
  - Define 종료 시 해당 단계에서 바꾼 파일만 커밋한다. Define·Plan Round 중 커밋하지 않는다.
  - 다른 목표의 변경을 함께 스테이징하지 않는다.
- **C4 — 사용자 직접 호출과 판단**
  - 사용자가 직접 호출할 때만 시작한다. D2 설정과 스킬 본문에 이 정책을 명시한다.
  - 방향 선택·범위 확대·추가 실험·종료·채택은 사용자가 판단한다.
  - 허용된 범위의 제작·실행·관찰은 에이전트가 수행하며, 개별 구현 작업마다 재확인하지 않는다.
  - 설정이 제어하는 암시적 호출과 본문이 정하는 호출 후 판단 지점을 구분한다.
- **C5 — 실험 산출물의 보관·격리·커밋**
  - `.goal/<goal>/prototype/<experiment>/`에 질문·결과·실행 안내·필요한 산출물을 보존한다.
  - 기존 목표 폴더를 재사용한다. 단독 요청에서 폴더가 불명확하면 이름을 확인한다.
  - 브랜치/worktree·새 세션은 격리나 이동이 필요할 때 사용한다.
  - 단독 실험은 사용자가 종료를 판단한 뒤 해당 변경만 커밋한다.
  - 단계 중 호출한 실험은 부모 단계의 커밋 규칙을 따른다. 결과·증거를 임의로 삭제하지 않는다.
- **C6 — 탐색과 정식 구현의 구분**
  - 질문을 확인하는 데 필요한 작은 assertion·측정은 허용한다. 제품 수준의 테스트 절차는 공통 선행 조건으로 요구하지 않는다.
  - 제품 구현으로 자동 진행하지 않는다.
  - 프로토타입 코드를 정식 구현에 재사용할 때는 기존 구현·검증 품질 기준을 적용한다. 모든 코드를 반드시 삭제하거나 반드시 재사용하도록 정하지 않는다.

## Out of scope

- 기존 단계 스킬 수정·자동 호출 연결, 기존 워크플로 전반 재설계.
- 제품 완성·배포와 프로토타입의 자동 제품 반영.
- 대상 사용자 모집과 시장 수요 검증.
- 장기간의 효과 비교 연구, 시간 절감·판단 정확도 개선의 실증.
- 별도 목표인 HTML 제작 과정 개선.
- 호출·진행 평가를 위해 별도 요청 시나리오 세트를 만드는 작업. 기존 Q10의 명확/모호·비호출·범위 확대 시나리오 추가안은 채택하지 않는다.

## Evaluation

- 아래 항목은 모두 합의한 Criteria / Method / Evidence이다. 실제 평가와 판정은 Verify에서 진행한다.
- 평가 범위는 실제 적용 사례 세 건, 원문·설정·본문 대조, 실제 파일·실행 안내·Git 기록이다.
- **Seam / Interface**: `codebase-design`을 로드했다. 사용자와 확인 절차는 같은 Interface를 이용한다.
  - 스킬의 Interface: 명시 호출, 제공한 질문, 산출물과 결과 보고.
  - UI/로직 데모의 Interface: 실제 화면과 공개 조작부.
  - 기술 스크립트의 Interface: 공개 실행 명령·입력·출력.
  - 내부 함수를 그대로 따라가는 테스트나 별도 테스트 프레임워크를 필수로 만들지 않는다.
- 별도 요청 시나리오를 추가하지 않는다. 세 사례에서 관찰하지 못한 조건은 지침·설정 대조로 확인하고, 실제로 실행한 범위와 구분해 기록한다.

- **R1 — 지원 범위**
  - Criteria: 세 유형 각각에서 질문에 맞는 관찰과 한계가 드러난다. 채택되지 않거나 부정적 답이 나온 사례도 유효하다.
  - Method: 실제 적용을 유형별 한 건씩 해당 공개 Interface에서 확인한다.
  - Evidence: 유형별 요청·실행 안내·산출물과 화면/사용자 판단·상태 변화·실제 실행 출력, 결과와 한계.
- **R2 — 독립 사용과 복귀**
  - Criteria: 직접 호출한 스킬로 사용할 수 있고 결과를 보고해 원래 논의로 돌아간다. 기존 단계 연결 수정이 필요하지 않다.
  - Method: 세 실제 사례의 호출·진행·결과 보고와 스킬 본문을 대조한다. 기존 단계 파일 변경 여부를 확인한다.
  - Evidence: 호출 요청·결과 응답·본문, 변경 파일 목록.
- **R3 — 작은 제작과 피드백**
  - Criteria: 질문에 맞는 형태로 진행하고 이미 제공된 정보를 활용한다. 유형별 제작 규칙과 불필요한 선행 절차를 요구하지 않는 규칙이 본문 및 실제 관찰된 진행에서 일치한다.
  - Method: 세 사례의 질문·추가 질문·제작 형태·사용자 피드백과 본문을 대조한다. 실행하지 않은 분기는 본문 검토로 확인한다.
  - Evidence: 입력 요청·대화 기록·유형별 산출물·실행 기록과 대응 지침.
- **R4 — 확인한 만큼만 보고**
  - Criteria: 보고가 실제로 확인한 내용과 맞는다. 사용자 피드백이나 실행 증거가 없으면 미확인 또는 사용자 선택 대기로 남긴다.
  - Method: 세 사례의 결과 보고를 화면·상태 변화·실행 출력·사용자 응답과 대조한다. 관찰하지 않은 조건을 확인했다고 보고하지 않았는지 본다.
  - Evidence: 실제 관찰 자료와 그에 대응하는 결과 보고. 미확인인 내용과 이유.
- **C1 — 근거 추적**
  - Criteria: 채택한 규칙의 출처와 조정 이유를 추적할 수 있고 세 사례의 실제 적용 기록이 있다.
  - Method: 출처·채택/조정 대응 기록을 원문과 대조하고 R1의 사례 결과를 확인한다.
  - Evidence: 원문 경로/위치·채택 내용·조정 이유의 대응 기록, 사례별 결과.
- **C2 — 단계 원칙 유지**
  - Criteria: 사용자 요청 없이 다음 단계·제품 구현으로 진행하지 않고, 탐색 관찰과 최종 목표 판정을 구분한다. 기존 단계 스킬과 AGENTS.md가 바뀌지 않는다.
  - Method: 스킬 본문과 실제 사례의 종료 후 행동·결과 보고, 변경 파일 목록을 확인한다.
  - Evidence: 해당 지침·결과 응답·실행 기록, Git 변경 목록.
- **C3 — 현재 문서·커밋 규칙**
  - Criteria: 목표 문서가 지정 폴더에 있고 Define 종료 시 해당 변경만 커밋한다. Round 중 커밋하지 않는다.
  - Method: 경로와 `git diff/status/log`로 변경 범위·커밋 시점을 확인한다.
  - Evidence: 목표 문서 경로, Define 완료 커밋과 변경 파일 목록.
- **C4 — 직접 호출과 사용자 판단**
  - Criteria: 새 스킬의 설정에 `policy.allow_implicit_invocation: false`가 있고 본문에 직접 호출·판단 주체를 명시한다. 실제 적용에서 에이전트는 허용된 작업을 수행하고 사용자 선택을 대신 확정하지 않는다.
  - Method: 공식 Codex 설정과 산출물을 대조하고 세 실제 사례의 호출·진행·결과 보고를 확인한다. 별도 비호출/범위 확대 시나리오는 만들지 않는다.
  - Evidence: 설정 파일·본문, 실제 요청·응답·실행 기록. 설정 대조와 실제 런타임 관찰의 범위를 구분한 기록.
- **C5 — 보관·격리·커밋**
  - Criteria: 지정 경로에 질문·결과·실행 안내·필요한 산출물이 보존된다. 조건에 맞게 격리와 사용자 종료 판단·부모 단계 커밋 규칙을 적용한다.
  - Method: 실제 파일과 실행 안내, `git diff/status/log`로 확인한다. 사례에서 발생하지 않은 조건은 본문 규칙을 대조하며 불필요한 worktree·세션·커밋을 만들지 않는다.
  - Evidence: 저장 파일·실행 안내·Git 기록, 조건부 규칙의 본문 위치와 실제 적용 여부.
- **C6 — 탐색과 정식 구현**
  - Criteria: 필요한 작은 측정을 허용하고 제품 테스트 절차를 일괄 강제하지 않는다. 자동 제품 반영을 하지 않으며 코드 재사용 시 정식 품질 기준을 적용한다고 명시한다.
  - Method: 본문과 실제 사례의 실행·측정·종료 행동을 확인한다. 이번 목표에서 제품 재사용 구현은 하지 않으므로 재사용 규칙은 본문 검토로 확인한다.
  - Evidence: 해당 지침·최소 실행/측정 기록, 변경 파일 목록.

## 참고 근거와 조정의 기준

- 아래는 Define의 근거다. 구현 후 채택된 지침과 원문의 대응 기록을 C1 기준으로 남긴다.
- [Matt prototype](../../docs/matt-skills/prototype/SKILL.md:8): 질문이 산출물 형태를 정함. [UI](../../docs/matt-skills/prototype/UI.md:38)의 기본 3안과 [LOGIC](../../docs/matt-skills/prototype/LOGIC.md:37)의 상태·조작·시나리오를 참고한다.
- [Matt UI 사용자 판단](../../docs/matt-skills/prototype/UI.md:94), [LOGIC 관찰과 종료](../../docs/matt-skills/prototype/LOGIC.md:52): 사용자가 보고 조작하고 답과 산출물을 보존한다.
- [pstack prototype](../../docs/pstack/skills/poteto-mode/playbooks/prototype.md:7): 질문을 좁히고 작은 화면/스크립트에서 관찰한 근거를 보고한다. 특정 API·권한을 일괄 시험한다는 원문 규칙은 아니며 실제 조건 선택은 질문에 맞춘다.
- [Superpowers spike](../../docs/superpowers/brainstorming/SKILL.md:104): 작은 탐색 후 배움을 대화로 돌려준다. [판단 주체 구분](../../docs/superpowers/brainstorming/SKILL.md:57)을 참고한다.
- [ask-matt](../../docs/matt-skills/ask-matt/SKILL.md:20), [독립 도구 설명](../../docs/matt-skills/ask-matt/SKILL.md:87): 대화에서 prototype으로 우회할 수 있다. 사용자 직접 호출 전용은 원문 전체의 공통 규칙이 아니라 이번 흐름의 선택이다.
- [Matt phase boundaries](../../docs/matt-skills/ask-matt/PHASE-BOUNDARIES.md:21): 현재 세션에서 계속할 수 있는지 먼저 판단하며 항상 새 세션·handoff를 요구하지 않는다.
- [writing-skills](../../docs/superpowers/writing-skills/SKILL.md:413): 절차의 적용·변형·정보 누락 평가를 참고했다. 이번에는 사용자 결정에 따라 별도 요청 시나리오 세트를 제외하고 실제 세 사례와 지침 대조로 평가한다. 유형별 한 건은 원문이 정한 수량이 아닌 합의한 로컬 기준이다.
- [공식 Codex Build skills](https://learn.chatgpt.com/docs/build-skills#optional-metadata): `agents/openai.yaml`의 `policy.allow_implicit_invocation: false`는 암시적 호출을 비활성화하고 명시적 호출을 유지한다. 호출 후 사용자 판단 지점은 본문에 명시한다.
- 참고 원문에는 이 방법의 시간 절감·판단 정확도를 실증한 결과가 없다. Define에서 확인한 것은 원문 절차와 공식 설정이며 실제 스킬 동작을 검증한 결과는 아니다.

## 합의 기록과 종료

- Q1–Q3: 사용자가 “모두 예”로 세 지원 범위, 독립 보조 스킬, 원문 추적·실제 적용 평가를 승인했다.
- Q4–Q9 보완: 사용자 직접 호출·사용자 판단을 기준으로 근거를 먼저 제시해 질문을 재작성했다. 사용자가 “accept all”로 승인했다. 기존 단계의 연결 수정 제안은 제외됐다.
- Q10–Q12: 초기 Q10의 추가 요청 시나리오 평가안은 거절됐다. Q11은 쉽게 설명했고 Q12의 `s`는 승인으로 추정하지 않았다.
- 최종 재질문: Q10을 실제 세 사례·설정/본문 확인으로 줄이고, Q11을 확인한 내용과 보고의 일치 확인으로 설명했다. Q12는 파일·실행 안내·Git 기록 확인으로 재확인했다.
- 최종 사용자 응답: **“모두 동의”**. 위 최종 Evaluation을 승인했다. 이전의 더 넓은 시나리오 평가안은 이 합의로 대체된다.
- 사용자가 실제 문구 정의를 추가로 요청해 Define을 재개했고, Q13의 문구 동의로 보완을 마쳤다. 기존 요구사항·제약·평가는 유지한다.
- 종료 기준 충족: 여섯 항목과 R1–R4·C1–C6의 Criteria / Method / Evidence가 있고, 실제 문구에도 합의했다. Frontier는 비었으며 새 미결정이 없다.
- 다음 단계 진입은 사용자 요청에 따른다.

## 실제 문구 Define 보완

- 추가 요청: “실제 어떤 멘트로 구성할지도 define하자”.
- 확정 문구: [skill-draft.md](skill-draft.md). 새 스킬의 설명·본문에 넣을 실제 지시문이다. 사용자에게 매번 같은 멘트를 말하게 하는 응답 템플릿은 요구하지 않는다.
- Q13 응답: 사용자가 **“동의”**로 제시한 문구 전체를 승인했다. 승인한 문구를 그대로 보존했다. 현재 frontier는 없다.
- 확정 문구는 Matt의 질문 우선·UI 3안·로직 상태/조작, pstack의 작은 실행·관찰, Superpowers의 최소 테스트·대화 복귀를 참고했다. 직접 호출·사용자 종료 판단·단일 UI 1안·.goal 보관은 기존 합의에 따른 로컬 조정이다.
- C1의 출처 기록과 C3의 현재 Define 규칙은 스킬 제작에 적용되므로 매 호출의 필수 작업으로 본문에 옮기지 않았다.
- 문구 확인은 기존 평가의 지침 대조에 포함한다. 동작 평가를 문장 일치 테스트로 대신하지 않는다.
- Define 문구 보완을 마쳤다. `goal.md`와 확정 문구 파일만 보완 커밋에 포함한다. 실제 스킬 구현이나 평가 사례 실행은 수행하지 않았다.
