# Analysis: HTML 제작이 매끄럽지 않았던 원인과 개선 조언

작성: 2026-10-28. 같은 workflow-prototype 목표의 후속 Analysis.
대상: 사용자의 “html로 만들어줘” 요청부터 HTML을 .goal/workflow-prototype에 보관한 과정.
근거: 이 대화에 남은 도구 호출·오류·성공 결과, AGENTS.md, 최종 HTML과 analysis.md.
도구를 다시 실행해 장애를 재현하지 않았다. 이 문서에 쓰는 진단은 관찰과 추론을 구분한다.

## Concept

### 1. 파일 제작, 파일 확인, 사용자가 열 수 있게 전달하기는 서로 다른 작업이다

- 제작: 내용이 들어 있는 HTML을 저장한다.
- 확인: 문서 구조·링크·필요한 상호작용과 화면을 확인한다.
- 전달: 사용자가 계속 보관할 위치의 파일 링크를 제공한다.

이번에는 제작을 마치기 전 브라우저 준비를 병행했고, 임시 위치에서 확인한 결과를 전달한 뒤, 별도 요청을 받고 저장소로 옮겼다.
각 작업의 완료 조건과 저장 위치를 일찍 정하지 않은 것이 왕복의 한 원인이다.

### 2. “Playwright 호환”은 모든 API와 실행 환경이 같다는 보장이 아니다

브라우저 제어 도구에는 지원 API, 호출 간 세션 수명, 파일 접근 권한, 캡처 저장 영역이 각각 있다.
이 도구에서 확인한 범위를 넘어 일반 Playwright의 사용법을 가정하면, 검증하려는 HTML과 무관한 실패가 생길 수 있다.

### 3. 검증 범위는 산출물의 규모와 실패 영향에 맞춰야 한다

분석 내용을 읽는 로컬 HTML의 핵심은 내용, 가독성, 접근 가능한 파일이다.
상호작용을 추가했다면 그 동작은 확인해야 한다. 다만 모바일·인쇄·새 도구 기능까지 확인 범위를 계속 늘리면 추가 기능의 검증 비용이 본래 작업을 압도할 수 있다.
검증을 줄이라는 뜻은 필요한 확인을 생략하라는 뜻이 아니라, 필요한 확인과 선택적 개선을 미리 구분하라는 뜻이다.

## Context

### 관찰된 사건과 근거

| 관찰 | 기록에 남은 결과 | 확실하게 말할 수 있는 것 |
|---|---|---|
| 폴더명을 질문했지만 답변이 오기 전에 HTML 제작 요청이 이어졌다 | 임시 위치에 HTML을 전달하고, 이후 “goal에 만들어줘” 요청으로 저장소에 보관했다 | 명명 미결정이 최종 보관을 늦췄고, 사용자의 추가 요청이 필요했다 |
| 큰 HTML을 한 번에 apply_patch로 작성하려 했다 | 여러 대기 호출에도 완료 응답이 없어 호출을 중단했다 | 그 호출이 응답하지 않은 사실은 확인된다. 내부 지연 원인은 확인되지 않는다 |
| 작성 방식을 변경했다 | Python 파일 쓰기로 HTML이 저장됐다 | 파일 저장 작업 자체를 완료할 다른 허용된 방법은 있었다 |
| Aside CLI를 샌드박스에서 호출했다 | “connect EPERM 127.0.0.1:21420” | 로컬 브라우저 연결이 샌드박스에서 차단됐다. 승인된 외부 실행이 필요했다 |
| 파일 URL을 열려 했다 | “Cannot navigate to a file URL without local file access.” | 당시 세션에는 필요한 로컬 파일 접근 권한이 없었다. Aside 전체가 파일 URL을 지원하지 않는다고 일반화할 근거는 아니다 |
| 임시 HTTP 서버를 시작했다 | 샌드박스의 socket bind가 PermissionError로 실패했고 외부 실행에서 성공했다 | 로컬 미리보기에도 실행 환경의 권한 제약이 있었다 |
| 다음 one-shot 호출에서 앞서 연 탭을 찾았다 | find 결과가 없어 targetId 접근이 실패했다 | 다음 호출에도 탭이 존재한다고 가정한 코드가 잘못됐다. 세션 수명을 확인했어야 했다 |
| snapshot에 보인 이름으로 정확한 role 선택자를 사용했다 | “Role selector not found” | snapshot 표시 이름과 해당 호출의 선택자가 매칭되지 않았다. 공백 처리 등 내부 원인은 미확정이다 |
| 생성한 HTML의 ID로 선택했다 | 네 질문 탭과 다섯 단계 탭의 변경 결과가 snapshot에 나타났다 | 해당 방식으로 필요한 아홉 개의 선택 동작은 확인했다 |
| page.setViewportSize를 호출했다 | 해당 줄에서 “TypeError: not a function” | 이 세션에서 그 방식의 뷰포트 변경을 사용할 수 없었다. 예정했던 모바일 화면 확인은 완료하지 못했다 |
| 캡처 경로를 셸 작업의 임시 폴더로 지정했다 | “escapes the session directory” | 브라우저의 캡처 저장 영역이 셸 파일시스템과 다르다 |
| 캡처를 세션 내부 상대 경로에 저장했다 | 캡처 생성 후 view_image로 데스크톱 화면을 확인했다 | 데스크톱 표시를 실제로 확인했다 |
| 마지막으로 .goal에 보관했다 | HTML의 로컬 링크를 상대 경로로 바꾸고 분석 문서와 함께 커밋했다 | 최종 보관은 완료됐다. 커밋은 2a7df43이다 |

폴더 확인 규칙의 출처는 [AGENTS.md](../../AGENTS.md)의 “Reuse the goal folder name agreed with the user; if the target is unclear, confirm it first.”다.
확인 질문 자체는 그 규칙에 근거했다. 그러나 임시 파일을 최종 전달하고 나중에 같은 기본 폴더명으로 옮긴 흐름은 일관되지 못했다.

브라우저 가이드는 사전에 읽었다. 따라서 단순히 “가이드를 읽지 않아서”라고 설명할 수 없다.
가이드에 있던 세션·파일 경계와, 실제로 확인되지 않은 API 지원 범위를 실행 계획에 충분히 반영하지 못한 것이 더 정확한 진단이다.

### 최종 산출물에서 확인된 범위

- 완료: HTML 구조와 JavaScript 문법, 문서 내 링크와 로컬 참조 파일, 네 질문 탭과 다섯 단계 탭, 데스크톱 캡처.
- 완료: 저장소 보관 후 로컬 링크의 상대 경로 변환과 파일 존재 확인.
- 미완료: 실제 모바일 뷰포트에서의 렌더링 확인, 실제 인쇄·PDF 출력 확인.
- 위 두 미완료 항목이 실제로 잘못됐다는 증거는 없다. 확인 완료로 주장할 근거도 없다.

## Problem

### 1. 주된 원인은 실행 범위와 종료 기준을 좁히지 못한 진행 판단이다

사용자는 분석 내용을 HTML로 요청했다.
표와 간단한 흐름도로 핵심을 전달할 수 있었지만, 질문·단계별 선택 UI, 키보드 조작, 인쇄용 전체 표까지 추가했다.
이 기능들은 설명에 도움이 될 수 있지만, 필수와 선택을 구분하지 않아 제작과 확인 범위가 넓어졌다.

이후 도구 실패를 만날 때마다 파일 URL, 서버, 탭 재연결, role 선택자, 뷰포트 변경, 캡처 경로를 순서대로 탐색했다.
각 실패가 새 확인 작업을 만들었고, 어디까지 확인하면 전달할지의 기준이 늦게 잡혔다.
기능이 많다는 사실만으로 잘못은 아니다. 추가 기능과 도구 탐색의 비용을 통제하지 못한 점이 문제다.

### 2. 브라우저 도구를 일반 Playwright처럼 가정했다

호출 사이에 탭이 남아 있다고 가정했고, 지원을 확인하지 않은 API를 썼으며, 캡처에 셸의 임시 경로를 사용했다.
HTML 기능의 오류를 확인하기 전에 확인 도구 사용법에서 반복 실패했다.
이는 주로 제 도구 사용 판단의 문제다. 실제 샌드박스 제약은 있었지만 그 제약만으로 반복 시도 전체가 설명되지는 않는다.

### 3. 무응답 이후 전환이 늦었다

apply_patch가 응답하지 않는 동안 비슷한 대기를 반복했다.
대기 결과에는 새로운 진단 정보가 없었다.
그 원인이 도구 처리 지연, 승인 처리, 다른 내부 문제 중 무엇인지는 기록으로 판단할 수 없다.

개선 방향은 적당한 대기 후 상태·오류·승인 필요 여부를 확인하고, 거부나 권한 제한을 우회하지 않는 범위에서 허용된 대체 방식으로 전환하는 것이다.
원인을 확인하지 않은 채 “임시 폴더라 차단됐다”거나 “apply_patch가 고장났다”고 단정하면 잘못된 처방이 된다.

### 4. 저장 위치 규칙이 작은 작업의 미결정까지 크게 만들었다

현재 규칙은 목표 내용이 불분명한 경우와 폴더의 문자열만 미정인 경우를 구분하지 않는다.
새 목표의 이름을 묻는 것은 규칙 준수였지만, 사용자는 분석과 HTML을 계속 요청했고 최종 파일은 임시 위치에 남았다.
나중에는 “goal에 만들어줘”라는 요청만으로 처음 제안한 workflow-prototype을 사용했다.

앞으로는 기존 목표가 있으면 재사용하고, 새 목표에서 단순 이름만 미정이면 기본 이름을 정해 알리며, 목표의 소속·범위가 불분명할 때 질문하는 규칙이 더 잘 맞아 보인다.
이는 현행 AGENTS.md를 바꾸자는 제안이다. 현재 규칙이 이미 자동 명명을 허용한다는 주장은 아니다.

### 개선 조언의 우선순위

| 우선순위 | 개선 | 이번 사례에 적용하면 |
|---|---|---|
| 1 | 저장 위치와 핵심 완료 조건을 먼저 정한다 | 동일 목표의 HTML은 해당 .goal 폴더에 보관. 내용·읽기·파일 링크를 기본 완료 조건으로 삼는다 |
| 2 | 작동하는 작은 파일부터 저장한다 | 완성 문서를 한 번에 큰 도구 호출로 보내기 전에 읽을 수 있는 HTML 파일을 확보한다 |
| 3 | 필요한 상호작용만 추가한다 | 표·흐름도로 설명이 되면 정적으로 끝내고, 선택 동작이 이해에 유용할 때 좁게 추가한다 |
| 4 | 브라우저 확인은 지원되는 방식으로 한 세션에 묶는다 | 파일 열기 조건·세션 수명·선택 방식·세션 내부 캡처 경로를 확인한 뒤, 필요한 동작과 화면만 점검한다 |
| 5 | 실패의 종류에 따라 대응한다 | 권한 오류는 필요한 승인을 받고, API 미지원은 지원되는 방법으로 바꾸며, 무응답은 새 정보 없는 대기를 반복하지 않는다 |
| 6 | 검증 한계를 정확히 보고한다 | PC와 선택 UI 확인 완료, 모바일·실제 인쇄 미확인처럼 사실을 구분해 전달한다 |

승인 요청 중에는 샌드박스 규칙상 필요한 것이 있었다. 이를 없애기 위해 권한 경계를 우회해서는 안 된다.
줄여야 할 것은 필요한 승인이 아니라, 사용할 경로를 뒤늦게 하나씩 발견하면서 생긴 반복 시도와 확인 범위의 확대다.

### 규칙을 바꾼다면 적합한 수준

아래는 조언이며, 이 세션에서 AGENTS.md나 스킬 파일을 수정하지 않았다.

1. AGENTS.md의 폴더 규칙을 “기존 목표 재사용 / 단순 이름은 기본값 / 소속·범위가 불명확하면 질문”으로 구분한다.
2. HTML 산출물의 기본은 단일 파일, 상대 경로, 외부 의존성 최소화로 둔다.
3. 브라우저 확인은 실제 지원 API와 세션 내부 경로를 사용하고, 산출물에 필요한 확인이 끝나면 종료한다.
4. 반복해서 같은 형식의 문서를 만든다면 얇은 HTML 템플릿을 재사용한다. 지금 발견한 문제만으로 큰 새 제작 스킬을 먼저 추가할 필요는 확인되지 않았다.

## 남은 불확실성

1. 최초 apply_patch 호출이 응답하지 않은 내부 원인은 확인하지 못했다.
2. 대기 시간 중 도구 처리, 승인 처리, 다른 지연이 각각 얼마나 차지했는지 분해할 수 없다.
3. 탭 이름의 role 매칭 실패가 공백 처리, 선택자 구현 또는 다른 내부 동작 중 무엇 때문인지는 확인하지 못했다.
4. 최종 HTML의 실제 모바일·인쇄 결과는 미확인이다.
5. 폴더 자동 명명과 HTML 기본 완료 조건의 규칙 변경은 아직 사용자와 합의하지 않았다.
