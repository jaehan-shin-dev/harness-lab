# Prototype

사용자가 직접 호출했을 때, 판단할 질문에 답하는 가장 작은 산출물을 만들고 관찰한 내용과 한계를 돌려준다.

## 시작

이미 제공된 목표와 맥락을 활용해 이번에 확인할 질문을 좁힌다. 질문이 분명하면 바로 진행하고, 필요한 사용자 결정이 빠졌을 때만 묻는다.
기존 목표 폴더를 재사용한다. 어느 `.goal/<goal>/`에 기록할지 불명확하면 먼저 이름을 확인한다.

## 만들고 관찰하기

질문에 답할 가장 작은 형태를 고른다.

- UI 비교는 우선 3안을 만들어 사용자가 비교·선택할 수 있게 한다. 한 아이디어를 보는 요청이면 1안도 허용한다.
- 상태·로직은 관련 상태와 시나리오를 드러내고 사용자가 직접 조작할 수 있게 한다.
- 기술 가능성은 질문이 의존하는 실제 조건을 실행한다. 실제로 확인한 부분과 대체한 부분을 구분한다.

사용자가 산출물을 직접 보고 조작하거나 실행 결과를 확인할 수 있게 제시한다.
고정 시간·총 반복 횟수, 별도 제품 goal·ticket, 제품 수준의 테스트 절차를 공통 선행 조건으로 요구하지 않는다. 질문 확인에 필요한 작은 assertion·측정은 사용한다.

## 사용자 판단

허용된 범위의 제작·실행·관찰은 개별 작업마다 재확인하지 않고 수행한다.
방향 선택·범위 확대·추가 실험·종료·채택은 사용자가 판단한다. 에이전트의 선택을 사용자 합의로 기록하지 않는다.

## 결과 보고

질문에 대해 관찰한 것, 알게 된 것, 한계와 남은 선택을 보고하고 원래 논의로 돌아간다.
화면 선호는 사용자 판단, 로직은 상태 변화, 기술 가능성은 실제 실행을 근거로 삼는다.
확인하지 못한 사실은 미확인으로, 사용자가 고르지 않은 방향은 사용자 선택 대기로 남긴다. 부정적인 결과도 질문에 답한다면 유효한 발견이다.

탐색 관찰을 최종 goal.md Evaluation에 따른 목표 달성 판정으로 대신하지 않는다. 다음 단계나 제품 구현은 사용자 요청에 따라 진행한다.
정식 구현을 요청받아 코드를 재사용할 때는 기존 구현·검증 품질 기준을 적용한다.

## 보관과 커밋

`.goal/<goal>/prototype/<experiment>/`에 질문·결과·실행 안내·필요한 산출물을 보존한다.
기본은 현재 작업 공간이며, 격리나 이동이 필요할 때 브랜치/worktree·새 세션을 사용한다.
단독 실험은 사용자가 종료를 판단한 뒤 해당 변경만 커밋한다. 단계 중 호출한 실험은 부모 단계의 커밋 규칙을 따르며 Define·Plan Round 중 커밋하지 않는다.
결과와 증거를 임의로 삭제하지 않는다.
